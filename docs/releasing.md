# BOS desktop release contract

Ordinary `pnpm package:mac`, `package:win` and `package:linux` create **BOS Staging** in `release-staging`, with `ai.bos.bot.staging`, the staging protocol and no updater feed. They never publish. Staging Linux DEBs use separate `/opt/BOS Staging`, `bos-staging` launcher and `bos-staging-browser` AppArmor install/remove hooks; their exact policy never targets the live BOS installation. Explicit `package:<platform>:live` creates **BOS Bot** in `release`, with `ai.bos.bot`, `bosbot`, `BOS-Bot-*` artifacts and the sole updater destination `firazfhansurie/bos-bot`. The release workflow is manual only; it neither mirrors upstream releases nor dispatches npm/Docker publication.

Live packaging requires a stable semantic package version and clean source checkout. Every package records the current full git commit in `bosSourceCommit`. The shared release-contract check reads the actual packaged ASAR metadata and app-update.yml; its platform manifests must agree with the pinned workflow commit and version before assembly. Staging checks reject any updater file. Run `pnpm test:release-contract` for configuration and negative regression coverage.

Mac release prerequisites are `MAC_CERT_P12_BASE64`, `MAC_CERT_PASSWORD`, `APPLE_API_KEY_P8_BASE64`, `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER_ID`. The workflow imports Developer ID into a temporary keychain, verifies the app and native signatures before notarization, waits for accepted notarization, staples, regenerates zip/blockmaps and feed hashes, then checks the final bytes. Supplying environment values is only a prerequisite check; it proves no certificate or notarization result by itself.

Windows requires `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` secrets and the `BOS_WINDOWS_PUBLISHER` repository variable containing the certificate's stable simple publisher name. The workflow maps those signing secrets to electron-builder's `CSC_LINK`/`CSC_KEY_PASSWORD`. Live config forces signing and updater signature verification; the packaged updater publisher must match the configured name. Authenticode must report Valid and the actual signer must match. No certificate is provisioned by these changes. Keep the publisher stable; certificate migration needs separate compatibility review.

Linux release gates verify BOS-specific DEB metadata, desktop identity, installed upgrade permissions, Chromium sandbox, exact BOS browser AppArmor policy, and unpacked/AppImage/installed runtime smoke. The upgrade test refuses a pre-existing BOS installation and runs only as root on an ephemeral CI runner. Local synthetic fixtures do not prove these installed gates passed.

All intended artifacts are built from one pinned commit. Assembly requires an exact asset set, matching manifest commits and versions, and feed hashes matching staged bytes. It creates a BOS-owned draft only after those gates. Publication requires the explicit dispatch `publish` flag. Configuration changes, local tests, runner packaging, draft assembly, publication, installation and installed-device verification are distinct states. No local validation authorizes installation or publication.

Remaining external gates: approved stable release version, verified BOS-owned repository and public update access, real Mac signing/notary credentials, real Windows certificate and stable publisher, BOS Linux installed acceptance, platform runner builds, and explicit distribution/install approval.

## Desktop feed parity and rollout

A mac release requires Windows installers for the same stable version. Before uploading or publishing a generic feed, run `node scripts/release-publish-guard.mjs <feedDir> <version>`. It rejects missing or empty Windows artifacts and mismatched `latest-mac.yml` / `latest.yml` versions. The canonical release and legacy mirror workflows invoke this guard before creating or publishing releases, in addition to their complete asset, source and hash checks. Changing a feed version by hand does not replace rebuilding the matching installer.

Set native electron-updater rollout with `node scripts/release-stage.mjs <feedDir> 10`, then `50`, then `100` after reviewing crash, heal and update coverage. Both feeds receive the same integer `stagingPercentage` (0–100); file order, hashes and release notes are retained. The script validates both feeds and matching desktop artifacts before changing either feed. It edits local files only. Publishing those files remains a separate authorized action; upload the two feeds together after the parity and hash gates. Lowering the percentage does not remove a version already offered to an installation. Rollback requires the previous known-good build packaged as a newer semantic version.

Never raise `minVersion.desktop` in `bosbot.my/api/app-config` before both published feeds (`latest-mac.yml` and `latest.yml`) carry that version or newer at 100% availability. The desktop only blocks while a qualifying update is downloading or installing, so an early floor degrades to a dismissible "update required" card rather than a lockout, but every install below it still loses quiet staged rollout and sees a failure card until the feed catches up. Raise the floor last, after the feed upload is verified; lower it first when rolling back.

## No-downgrade guard

Every macOS package is stamped at `Contents/Resources/build-commit.json` by `scripts/after-pack.mjs` (source commit from `bosSourceCommit` plus the sha256 of the `server` and `ui` trees; a real package without a commit fails to build). The 1.3 updater runs `Contents/Resources/updater/no-downgrade.py check` on the staged bundle right after the launchd preflight and refuses, before anything is locked or stopped, unless the candidate is stamped, its commit descends from the running build, is reachable from the release branch (`BOS_UPDATE_RELEASE_BRANCH`, default `release/bos-1.0`) and is exactly the head of the prod branch (`BOS_UPDATE_PROD_BRANCH`, default `prod`). Ancestry is checked in the canonical checkout named by `BOS_UPDATE_REPO` or by the ledger at `<data>/updates/live-build.json`. The ledger identifies builds from before the stamp existed: seed it once with `no-downgrade.py record --live "/Applications/BOS Bot.app" --commit <sha> --repo <checkout> --release-branch release/bos-1.0`. After a finished update the next boot records the new live bundle; `check --rollback` only admits a bundle byte-identical to the ledger's previous entry. The check is not only admission's: the detached job (`apply.py`, generated from `server/updater-apply-script.ts` into `<data>/updates/<id>/`) runs its own copy of `no-downgrade.py` (sha256 pinned in `plan.json`) before it stops the app, and a packaged build refuses an update plan that carries no guard, so a plan fed to it by hand is judged the same way; a refusal leaves the app running, untouched. `scripts/stage-update.ts` runs the same `check` before it copies a bundle into `updates/candidate` (`--rollback` for the previously-live build only). Hand-run installers that rename onto `/Applications/BOS Bot.app` outside these paths must call the same `check` before swapping, or be retired in favour of the button.
