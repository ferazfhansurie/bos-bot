# bos alpha: data and support

this overview describes the current local-host alpha. it is release documentation; it has not been published as a legal policy.

- conversations and attachments are stored by the mac hosting the conversation. people with access to that conversation can read its messages.
- invoking a bot sends the selected conversation context and supported attachments to the bot's configured model provider. that provider's account settings and terms apply.
- shared conversations use separate provider context. joining a chat does not grant access to the bot owner's private chats, local projects, connected apps or computer.
- paired iphones connect to their host. push notifications use apple's push service when configured. device tokens and notification settings are stored for delivery.
- connected homes exchange identity, shared bot availability and authorized conversation messages over their configured links.
- editing/removing messages changes the stored conversation. removing a member ends their future access; it cannot retract copies they already saw or exported.
- support: email ferazfhansurie@gmail.com for a privacy request. "tell firaz" sends only the note you explicitly choose to share, optional up/down rating and the install id to `https://bosbot.my/api/feedback`. turn ratings ask before sharing and send no message text or message id. nothing uploads automatically from the feedback screen. explicitly submitted feedback and diagnostics notify the existing internal support webhook.
- the bos server sends anonymous usage counts to `https://bos.aihlete.com/api/ping` on its first enabled run and at most once per rolling 24 hours afterward. the json fields are `install_id` (a random uuid v4 stored in the bos data directory, independent of account/device identity), `version`, `platform`, `arch`, `engines` (detected claude/codex cli names only), `bots`, `rooms`, `room_humans_max`, `room_bots_max`, and `event` (`first_run` or `daily`). rooms exclude direct messages; local rooms include their implicit human owner. no names, emails, messages, paths, prompts or tokens are sent. settings → general → "share anonymous usage counts" defaults on; turning it off stops future pings. `BOS_NO_PING=1` overrides that setting. paired phones use their host server's setting and do not send additional pings. requests time out after five seconds, failures are silent, and failed attempts are not retried within 24 hours. ordinary https transport also exposes the server's source ip to the receiver; it is not part of the json body.

before public release, review provider-specific telemetry, crash reporting, retention, deletion, backups and notification content against the final packaged configuration. publish the complete policy with the actual operator identity and service details.

2.1.3 adds the following:

- remote product config: `GET https://bosbot.my/api/app-config` on launch and every 15 minutes; cached locally with built-in offline defaults. no install id or identity is included. ordinary https exposes the source ip. config controls flags, minimum versions, banner, pricing, starter jobs and rollout percentages.
- installation events: `POST https://bosbot.my/api/events`, with `{install_id,version,platform,events:[{name,at,props}]}`. at most 50 events per batch, every 60 seconds and on shutdown. `at` is an ISO timestamp. the desktop uses the daily ping's random uuid. event names cover install/open, engine connected, first bot/message, explicitly confirmed first useful job, whatsapp/app connection, routine/phone/mod creation, update/heal outcomes and error class, plus named onboarding and feature interaction counts. properties are strictly allowlisted counts, booleans and engine/source/class/rating enums; chat, file names, paths, account ids, arbitrary strings, emails, prompts and tokens are discarded. the local persistent queue is capped at 500 events. failures retry on the next interval without interrupting work. turning off the existing anonymous-usage setting or setting `BOS_NO_PING=1` purges unsent events and aborts in-flight requests; a receiver may already have accepted an in-flight request.
- email claim: only an email typed during the current onboarding is held in memory and sent after completion to `POST https://bosbot.my/api/claim` with the install id, when anonymous usage is enabled. it can link only to the latest consented signup with the same email. it is stored separately from event batches; no email or existing profile is silently added to events. no email typed means no claim. a claimed email is self-reported, not verified identity or ownership proof.
- diagnostics: an explicit "send report" action posts the redacted diagnostic report to `https://bosbot.my/api/diag`, max 5 MiB. reports may have an install id or be anonymous. the receiver additionally removes common credentials, home paths and sensitive fields. no transcript is intentionally included. files are private (0600, report directories 0700). no automatic crash transcript upload occurs.
- phones: each phone has a separate persistent random installation id. native install/open/pair-success events use the same event endpoint, max 50 per batch, a bounded 200-event local queue and a 60-second/background flush. the phone's local switch and paired servers' anonymous-usage settings both apply. unknown/offline settings defer sends; an explicit server opt-out purges them. unpaired phones send nothing. iOS `push_ok` requires successful registration and confirmed server delivery configuration; android has no push success telemetry. debug/preview builds disable public telemetry.
- referrals: an optional invite link contains a one-way code derived from the install id; download rows record that referral. it is attribution only, never proof of a person or a purchase.
- receiver: events/claims/feedback are appended to private (0600) files on the BOS site server. requests are size capped and rate limited. the authenticated dashboard excludes known internal ids, development installs and `test-213-` ids; it labels counts as installation ids, not people. version coverage uses installations active in the last seven days. day-seven return requires seven elapsed days after first observation. retention/deletion policy still needs the public policy review above.
